# ADR 001: 采用 Agent-as-a-Tool 的 Multi-Agent 委托模式

- **状态**: Accepted
- **日期**: 2025-08-31
- **决策者**: Memoria 核心架构团队

## 背景与问题

随着 Memoria 的演进，系统需要同时承载：
1. 本地知识库的语义检索与文档分析（RAG）。
2. 受控主机的远程诊断与运维执行（SSH 命令、指标监控、日志分析）。
3. 跨域融合场景（例如：根据知识库中的排障手册，连接某台机器执行特定的诊断指令）。

如果使用单一的单体 Agent（Single Agent），随着注入的工具列表不断膨胀（检索工具、上传工具、主机命令工具、安全审批工具等），会导致模型注意力稀释、工具误用概率升高以及上下文窗口极大消耗。
若使用硬编码的流水线（DAG / StateGraph），则缺乏自由交互式问答的灵活性，无法动态根据用户自然语言意图来回往复切换专家域。

## 决策

我们决定在 `memoria/agents/` 中采用 **Agent-as-a-Tool（委托模式）**：
1. **主编排智能体（Orchestrator）**：作为与用户直接对话的入口根大脑，专注于意图解析、任务拆解与最终跨域答复聚合。
2. **专业子智能体（Sub-agents / Workers）**：
   - `kb_agent`：专精于知识检索、Top-K 筛选、重排与知识问答。
   - `host_agent`：专精于受控主机的命令生成、安全模式检查与受控运维操作。
3. **工具封装与调用**：子智能体通过系统函数工具（如 `delegate_to_kb_agent`、`delegate_to_host_agent`）的形式暴露给 Orchestrator。Orchestrator 在 ReAct 循环中根据需要唤起专家，专家在独立的子上下文与提示词约束下运行，并将最终输出作为 Tool Result 回传给主编排者。
4. **可观测追踪（Tracing & Spans）**：每次委托操作都会在 Trace 中沉淀为专属的 Child Span，流式推向前端可视化。

## 影响与权衡

### 正向收益
- **上下文隔离与专业度**：每个子智能体只拥有与其专精领域相关的提示词与工具集，大幅减少大模型“选错工具”的概率。
- **模块化与横向可扩展性**：未来新增“代码解释器专家”、“数据库专家”或“Web 浏览专家”时，仅需新增一个 Sub-agent 并注入为工具，不影响主干链路。
- **用户体验透明**：前端可以实时折叠显示“已委托知识库专家分析文档...”或“正在调用主机专家执行巡检...”。

### 潜在风险与缓解
- **多次 LLM 往返延迟（Latency）**：主智能体委托一次需要额外消耗 1~2 次 LLM 调用。
  - *缓解措施*：对子智能体输出进行轻量化约束，对于无需委派的普通闲聊直接由 Orchestrator 秒级应答。
